<objective>
Build the persistence layer the whole phase hangs from, and prove it by reading the file back off
the disk.

Every phrase in PROGRESS-01 and PROGRESS-02 maps to a recorded defect rather than to style. "The
progress-tracking system initializes without a script error" exists because the archived tracker
passed a nonexistent all-caps constant as its indent argument, so the registered autoload failed
to compile at every single startup. "Writes a matching entry" exists because nothing in the
archived game ever called the record function — progress was never written once, while the
project's own parent-dashboard document claimed it was. Those two failures are why D-42 insists
the proof is a file re-read and not a signal.

Research this session verified every load-bearing call against the real engine: the correct
stringify signature, that renaming over an existing file succeeds and fully replaces it, that a
missing file opens silently, and — the finding that shapes this plan most — that the static
one-call JSON parser prints an engine error line on bad input even while returning cleanly, which
the headless check reads as a failure. The instance parser returns an error code silently. That
single choice decides whether PROGRESS-01 can pass at all under this project's own check.

Purpose: this plan and plan 03-02 are the phase's foundation; no lesson can record anything until
this exists. It closes PROGRESS-01 and the mechanism half of PROGRESS-02. The full-stack half of
PROGRESS-02 — a real lesson completion writing a real entry — is closed by plan 03-03's tracer.

Output: `scripts/progress_tracker.gd`, its autoload registration in `project.godot`, and
`scripts/tools/probe_progress_persistence.gd`.

Decisions implemented: D-39, D-40, D-41, D-42.
</objective>

    write the whole history, then emit the saved signal. Exactly four keys and no more; a fifth
    field in a children's product is a privacy decision nobody made.
  - `get_entries() -> Array[Dictionary]` with a doc comment: return a duplicate of the history,
    not the live array, so no caller can mutate saved state through the accessor.
  - `_load_entries() -> Array[Dictionary]`: if the file does not exist, return an empty array —
    that is the ordinary first run on a new machine and the engine prints nothing for it. Open
    for reading; if the handle is null, warn with the bracketed class tag and the engine's own
    error string and return empty. Read the text and close the handle. Then construct a JSON
    instance and call its instance parse method on the text, keeping the returned error code. On
    a non-OK code, warn with the instance's own error message and line and return empty. This is
    the one call in the file that the whole of PROGRESS-01 rests on: the static one-call
    convenience parser prints an engine error line on invalid input even though it returns
    cleanly to the caller, and this repository's headless check fails the entire run on any such
    line — so a tracker written that way would turn the check red the moment a probe exercises
    the corrupt-file path, while the game itself recovered perfectly. Put that explanation in a
    comment on its own line, never as a trailing comment, because the acceptance criteria below
    count occurrences in the non-comment lines of this file. Then validate the parsed shape: a
    dictionary holding an entries key whose value is an array, or warn and return empty. Copy
    only dictionary elements into the typed result.
  - `_write_entries() -> void`: build a dictionary of the version constant and the history, then
    stringify it with a literal tab as the indent argument — `JSON.stringify(data, "\t")` is the
    verified signature. Do not pass any all-caps member of the JSON class as that argument; no
    such constant exists, and passing one is exactly why the archived autoload failed to compile
    at every startup. Open the temporary path for writing; if the handle is null, warn and
    return. Store the string, close the handle, then rename the temporary file over the real one
    using the absolute-path rename on the globalized forms of both paths, and warn with the
    engine's error string if it does not return OK. Research verified this rename returns OK both
    when no target exists and when one does, and that it replaces the target's content entirely.
