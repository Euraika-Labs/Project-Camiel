# Phase 2 — UI Design Contract

> Visual and interaction contract for the title screen, main menu, and 3D intro level
> (including its win-screen overlay). Generated by gsd-ui-researcher, verified by
> gsd-ui-checker. Consumed by gsd-planner and gsd-executor as the visual source of truth,
> and by `scripts/tools/probe_screen_flow.gd` for node names and focus order.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — Godot has no shadcn-equivalent component registry |
| Preset | not applicable |
| Component library | none — every Control is hand-built for this phase |
| Icon library | none — icons are drawn procedurally (see Icon Inventory) |
| Font | Godot's built-in default theme font, used directly (no new font asset). Bold weight is produced with a `FontVariation` resource (`variation_embolden = 1.0`) wrapping the default font, not a separate font file. |
| Shared theme resource | `res://assets/theme/ui_theme.tres` — every color/font-size/spacing token below is set on this one `Theme` resource and consumed by all three screens, so Phase 4's WCAG-AA contrast pass edits one resource instead of hunting through scenes. |

This project has no external UI package to enumerate (no `components.json`, no npm/Godot
asset-library dependency for UI). The `## Component Inventory` section from the standard
template is therefore omitted; the bespoke reusable component this phase produces
(`menu_button.tscn`) has its own contract section below instead.

## Design Tokens

Flagged **Phase-4-adjustable**: every hex value below lives in `ui_theme.tres` as a single
source of truth. Phase 4's WCAG 2.1 AA pass and its high-contrast toggle (`ACCESS-01`,
`ACCESS-02`) should only need to add a second `Theme` resource and a `contrast_changed`
signal-driven swap (per `CONCERNS.md`'s recommendation), not touch individual scenes.

### Color

| Role | Hex | Usage |
|------|-----|-------|
| Dominant (60%) | `#9ED1F2` | Screen background (`ColorRect`) on title screen and main menu — identical to `test_space.tscn`'s `WorldEnvironment.background_color`, so the 2D UI and the 3D world read as one continuous look |
| Secondary (30%) | `#FFF6E8` | Panel fills: `menu_button` background, `AudioPanel`, `WinPanel` |
| Accent (10%) | `#ED9E4D` | Reserved for exactly three things: (1) every `menu_button` icon glyph, (2) the static focus-ring border on a focused `menu_button`, (3) the 3D collectible's emissive material. Reused directly from `camiel.tscn`'s `Body` mesh `albedo_color = Color(0.93, 0.62, 0.3, 1)`, tying the collectible visually to Camiel. **Not** used as a full button background fill — that would blow the 10% budget across five+ buttons. |
| Text primary | `#1F3A56` | All label text (titles, button labels, slider labels) on both the dominant blue and secondary cream backgrounds |
| Panel border | `#D8CBB0` | 2px `StyleBoxFlat.border_color` on panels and button normal-state, for edge definition against the flat blue background — a substitute for drop shadows, which read as noisy at this simple-shape aesthetic |
| Destructive | not used this phase | No destructive action exists in this phase's scope (replay and return-to-menu are both non-destructive). Token reserved in `ui_theme.tres` as `#D9534F` for a future phase that needs it — do not wire it to anything now. |

### 3D World Materials (separate from the 60/30/10 UI budget above)

| Element | Hex | Usage |
|---------|-----|-------|
| Collectible emissive | `#ED9E4D` (same as UI accent) | `StandardMaterial3D.albedo_color` and `.emission`, `emission_enabled = true`, `emission_energy_multiplier = 1.5` — a warm, gentle glow, not a blinding one |
| Finish marker emissive | `#74C69D` | A calm sage green, deliberately a different hue from the collectible so a child never confuses "pick this up" with "walk through this" |

### Typography

| Role | Size | Weight | Line height |
|------|------|--------|-------------|
| Display (title screen "Camiel") | 64px | Bold (FontVariation embolden) | 1.2 |
| Heading (win-screen "Goed zo!") | 40px | Bold | 1.2 |
| Button label (all `menu_button` labels) | 28px | Regular | 1.2 |
| Small (slider row labels "Geluid" / "Muziek") | 20px | Regular | 1.4 |

Exactly 4 sizes, exactly 2 weights, per the spacing/typography discipline this contract follows.

### Spacing Scale

8-point scale, declared values only:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Not used at the Control-UI layer this phase (reserved for future icon-internal detail) |
| sm | 8px | `StyleBoxFlat` border widths, small internal padding |
| md | 16px | Gap between a slider row's icon, label, and slider |
| lg | 24px | Panel internal padding (`AudioPanel`, `WinPanel`); `VBoxContainer` separation between rows inside a panel |
| xl | 32px | Gap between the primary button and the audio panel on the main menu; screen outer margin |

> **Token-to-node binding for the 32px screen outer margin.** `CenterContainer` in Godot 4
> has **no** margin or padding theme property — it only centres its child, it does not inset
> it. So the outer margin is **not** set on `CenterContainer`. Realize it by wrapping the
> `Content` node in a `MarginContainer` and setting all four
> `theme_override_constants/margin_left|right|top|bottom` to `32`. Node order is
> `CenterContainer → MarginContainer → Content`. Do not approximate this with anchor offsets
> on the root `Control`; the `MarginContainer` keeps the value in one place where a Phase 4
> pass can retune it.
| 2xl | 48px | Gap between the two win-screen buttons — an explicit exception above the 8-pt default, sized deliberately large so a near-miss tap cannot activate the neighboring button |
| 3xl | 64px | Reserved for page-level top/bottom breathing room if a future screen needs it |

**Exception:** hit-target minimums (below) exceed the usual 44px mobile baseline. This
audience is age ~3 with imprecise pointer control (Design Priority 1); 44px is a baseline for
adult fingers, not toddlers holding a mouse or tapping a tablet with a parent's hand nearby.

### Hit Targets

| Control | Minimum size | Justification |
|---------|--------------|----------------|
| `menu_button` (all instances) | 280×112px | Roughly 2.5× the 44px mobile-accessibility baseline in each dimension. A 3-year-old's pointer control is imprecise; this size keeps the whole icon+label comfortably inside the reachable "aim zone" even with a shaky click or a fat-finger tap. |
| `HSlider` (SFX / BGM) | 320×56px interactive area | Sliders are inherently harder to land precisely than buttons. This control is intended for the co-present adult (PROJECT.md: "parents and teachers act as secondary users who co-play"), so it does not need toddler-grade tolerance — but it still gets a fat 56px track so it is not a fiddly desktop-app-sized widget. **See the accepted-risk note below.** |

> **Accepted risk — the 56px slider height is half the 112px button height on the same
> screen.** This is a deliberate decision, not an oversight. D-25 places the SFX slider on the
> main menu, which the child also navigates, and nothing prevents a child from tapping or
> tab-focusing the slider directly. The asymmetry is accepted because the consequence of a
> mis-hit is benign and instantly reversible — a volume change, audible immediately, with no
> state lost and no screen transition — whereas the 112px targets guard actions that *do*
> transition. If the Phase 2 closing playtest (D-30) shows a child fighting the sliders,
> raising the track to 112px or moving the audio panel behind a parent-facing control is a
> cheap follow-up. Phase 4 owns any broader accessibility retune.
| Gap between adjacent interactive controls | ≥32px (48px between the two win-screen buttons) | Prevents a near-miss on one control from landing on its neighbor — the direct fix for "pointer-imprecision tolerance" (Design Priority 1). |

### Corner Radii

| Token | Value | Usage |
|-------|-------|-------|
| sm | 8px | Not used this phase (reserved) |
| md | 16px | `HSlider` track corners |
| lg | 24px | `menu_button` background, `AudioPanel` |
| xl | 32px | `WinPanel` (the win screen reads as a distinct "badge" popped over the 3D world) |

### Motion (Calm requirement — Design Priority 3)

No flashing, no snap-scale, no camera jolts, anywhere in this phase's UI or level.

| Interaction | Treatment |
|-------------|-----------|
| Button hover | Background lightens by ~8% over 0.1s. No scale change. |
| Button press | Background darkens by ~8% over 0.05s. No scale change. |
| Focus ring | Static 4px `#ED9E4D` border. **Never pulses or blinks** — a static ring is visible enough without risking the startle a pulsing ring can cause. |
| Collectible pickup | Scale-pulse to 1.15× over 0.15s, then fade + `queue_free()` over 0.15s. No particle burst, no flash. |
| Win screen appearing | `WinLayer` fades in (`modulate.a` 0→1) over 0.3s — never an instant hard cut, never a sound sting synced to a visual flash. |
| Screen transitions | `change_scene_to_file` is an instant cut in Godot; no crossfade is specified for this phase (out of scope — a transition-fade layer is a nice-to-have for a later polish phase, not required by any requirement ID in scope). |

## Screen-by-Screen Specification

### 1. Title Screen — `scenes/title_screen.tscn`

Script: `scripts/title_screen.gd`.

```
TitleScreen : Control                          (root, full-rect anchor, script attached)
├── Background : ColorRect                     (full-rect anchor, color = #9ED1F2)
└── CenterContainer                             (full-rect anchor)
    └── Content : VBoxContainer                 (alignment = CENTER, separation = 32)
        ├── TitleLabel : Label                  (text = "Camiel", Display token)
        └── PlayButton : MenuButton             (instance of scenes/ui/menu_button.tscn)
                                                 unique name: %PlayButton
                                                 label_text = "Spelen", icon_kind = "play"
```

Layout: `CenterContainer` re-centers `Content` regardless of viewport size, so the screen
does not need per-aspect-ratio branches — this is the "layout at different aspect ratios"
answer for all three screens in this contract.

**Focus order:** `[%PlayButton]`. **Initial focus:** `%PlayButton` — call `grab_focus()` in
`_ready()`. There is exactly one focusable control, so the probe's "emit `pressed` on the
focused button" step has nothing else it could hit.

**Signal wiring:** `%PlayButton.pressed.connect(_on_play_button_pressed)` in `_ready()`.
Handler carries the D-15 one-shot `_transitioning` guard and calls
`get_tree().change_scene_to_file.call_deferred("res://scenes/main_menu.tscn")`.

### 2. Main Menu — `scenes/main_menu.tscn`

Script: `scripts/main_menu.gd`.

```
MainMenu : Control                              (root, full-rect anchor, script attached)
├── Background : ColorRect                      (full-rect anchor, color = #9ED1F2)
└── CenterContainer                              (full-rect anchor)
    └── Content : VBoxContainer                  (alignment = CENTER, separation = 32)
        ├── StartButton : MenuButton             (instance of scenes/ui/menu_button.tscn)
        │                                        unique name: %StartButton
        │                                        label_text = "Start", icon_kind = "walk"
        └── AudioPanel : PanelContainer          (background = #FFF6E8, border = #D8CBB0,
            │                                     corner_radius = 24, padding = 24)
            └── AudioRows : VBoxContainer         (separation = 24)
                ├── SfxRow : HBoxContainer         (separation = 16)
                │   ├── SfxIcon : Control          (script: vector_icon.gd, icon_kind="speaker",
                │   │                               size 32×32, color = #ED9E4D)
                │   ├── SfxLabel : Label            (text = "Geluid", Small token)
                │   └── SfxSlider : HSlider         unique name: %SfxSlider
                │                                    min=0 max=100 step=5 value=80
                │                                    tick_count=6, ticks_on_borders=true
                │                                    custom_minimum_size = (320, 56)
                └── BgmRow : HBoxContainer          (separation = 16)
                    ├── BgmIcon : Control            (vector_icon.gd, icon_kind="music_note",
                    │                                 size 32×32, color = #ED9E4D)
                    ├── BgmLabel : Label              (text = "Muziek", Small token)
                    └── BgmSlider : HSlider           unique name: %BgmSlider
                                                       min=0 max=100 step=5 value=60
                                                       tick_count=6, ticks_on_borders=true
                                                       custom_minimum_size = (320, 56)
```

**Why a BGM slider too (Claude's Discretion, D-25 area):** `set_bgm_volume` already exists
in the `AudioManager` public surface per D-23, the marginal cost of a second `HSlider` row is
low, and it lets the co-playing adult quiet the music while keeping SFX feedback audible
(or vice versa) — a real use case, not speculative scope. INTRO-06 only requires the SFX
slider to have an audible effect; the BGM slider is additive, not a substitute.

**Volume mapping:** both sliders emit `value_changed(value: float)` where `value` is 0-100.
`main_menu.gd` converts with `value / 100.0` before calling `AudioManager.set_sfx_volume()` /
`set_bgm_volume()`, which take a 0.0-1.0 linear float per D-23's kept API surface.
`main_menu.gd` also reads the current volume back from `AudioManager` in `_ready()` and sets
`slider.value` accordingly, so returning to this menu later does not reset the sliders to
their scene-file defaults.

**Focus order:** `[%StartButton, %SfxSlider, %BgmSlider]`, top to bottom, via explicit
`focus_neighbor_top` / `focus_neighbor_bottom` `NodePath`s (do not rely on Godot's automatic
spatial focus-neighbor inference — explicit wiring is what makes the order deterministic for
`probe_screen_flow.gd`). **Initial focus:** `%StartButton` — the primary action comes first.

**Signal wiring:** `%StartButton.pressed.connect(_on_start_button_pressed)`, same one-shot
`_transitioning` guard and deferred `change_scene_to_file("res://scenes/intro_level.tscn")`
as the title screen.

### 3. Intro Level — `scenes/intro_level.tscn` (3D scene + win-screen overlay)

Script: `scripts/intro_level.gd`. Root type is `Node3D` per D-27's retargeted assertion.

```
IntroLevel : Node3D                             (root, script attached)
├── WorldEnvironment                             (Environment: background_mode=1,
│                                                  background_color = #9ED1F2 — same
│                                                  hex as the 2D screens' Background,
│                                                  ambient_light_source=2,
│                                                  ambient_light_color=white,
│                                                  ambient_light_energy=0.5)
├── Sun : DirectionalLight3D                     (shadow_enabled=true, light_color slightly
│                                                  warm — Color(1, 0.98, 0.9) — soft daylight,
│                                                  not harsh white; same angle convention as
│                                                  test_space.tscn's Sun)
├── PlayerSpawn : Marker3D                       (records the reset transform "Nog een keer"
│                                                  returns Camiel to — see Replay Contract)
├── Camiel : (instance of scenes/camiel.tscn)     added to group "player" (see Open Questions —
│                                                  no committed scene currently does this)
├── [level geometry: Ground / Walls / RaisedStep — enclosed per D-17]
│    Exact dimensions and placement are PLAN.md's job, not this spec's — this contract only
│    fixes the visual/material language (see Design Tokens → 3D World Materials) and the
│    "fully enclosed, one low reachable rise" shape D-17 already locked.
├── Collectible : (instance of scenes/collectible.tscn)   unique name: %Collectible
│                                                  Area3D root; signal `collected` (no args)
│                                                  SphereMesh, radius ~0.3, emissive material
│                                                  per Design Tokens; continuous Y-axis spin
│                                                  at 30°/s (slow, calm — Design Priority 3);
│                                                  gentle vertical bob, amplitude 0.1m,
│                                                  period 2s, to read as "floating" per D-18
├── FinishMarker : (instance of scenes/finish_marker.tscn) unique name: %FinishMarker
│                                                  Area3D root; signal `finished` (no args)
│                                                  a standing TorusMesh "goal ring", radius
│                                                  ~1.2m, emissive material per Design Tokens
│                                                  (finish-marker green, distinct hue from the
│                                                  collectible's orange)
└── WinLayer : CanvasLayer                        unique name: %WinLayer, visible = false,
     │                                             process_mode = Always (so its buttons keep
     │                                             receiving input if gameplay is ever paused
     │                                             — see Open Questions)
     └── Scrim : Control                           (full-rect; ColorRect child, rgba(0,0,0,0.35)
         │                                          — a dim, not a block-out, so the 3D scene
         │                                          stays visible behind the panel: calm, not
         │                                          a jarring full-screen color swap)
         └── CenterContainer                        (full-rect)
             └── WinPanel : PanelContainer            (background = #FFF6E8, border = #D8CBB0,
                 │                                     corner_radius = 32, padding = 32)
                 └── WinContent : VBoxContainer        (separation = 32, alignment = CENTER)
                     ├── WinTitle : Label               (text = "Goed zo!", Heading token)
                     └── ButtonRow : HBoxContainer       (separation = 48 — the 2xl exception)
                         ├── ReplayButton : MenuButton    unique name: %ReplayButton
                         │                                 label_text = "Nog een keer"
                         │                                 icon_kind = "replay"
                         └── GoToMenuButton : MenuButton  unique name: %GoToMenuButton
                                                           label_text = "Naar menu"
                                                           icon_kind = "home"
```

**Signal architecture (D-20, D-19, D-14):**
- `%Collectible.collected` → `_on_collectible_collected()` in `intro_level.gd`: plays
  `AudioManager.play_sfx("collect")` exactly once (the existing one-shot `_touched` latch
  pattern inside `collectible.gd` itself guarantees "exactly once" — the level script does
  not need its own duplicate guard).
- `%FinishMarker.finished` → `_on_finish_marker_finished()` in `intro_level.gd`: shows the
  win screen (fades `%WinLayer` in per the Motion table) and calls `%ReplayButton.grab_focus()`.
  D-21: this connection exists regardless of whether `%Collectible` was ever triggered — the
  finish marker is not gated on the collectible.
- `%ReplayButton.pressed` → `_on_replay_button_pressed()`: **resets in place**, does not call
  `change_scene_to_file` or `reload_current_scene` (this is what D-28 means by "restarts
  without a scene round-trip"). Concretely: hide `%WinLayer`, move `Camiel` back to
  `PlayerSpawn.global_transform`, re-arm `%Collectible` (unhide it and re-enable its Area3D
  monitoring if it was collected).
- `%GoToMenuButton.pressed` → `_on_go_to_menu_button_pressed()`: the same one-shot
  `_transitioning` guard as the other two screens, deferred
  `change_scene_to_file("res://scenes/main_menu.tscn")`.

**Focus order:**
- Gameplay has no Control-node focus (movement is via InputMap actions per D-07, not UI
  focus navigation).
- Win-screen overlay: `[%ReplayButton, %GoToMenuButton]`, left to right. **Initial focus:**
  `%ReplayButton` — set when the overlay becomes visible (in
  `_on_finish_marker_finished()`), not in `_ready()`, since the layer starts hidden. Replay
  is the encouraging default (try again, no dead end) rather than exiting to the menu.

## `menu_button` Component Contract

`scenes/ui/menu_button.tscn` + `scripts/ui/menu_button.gd` — the single reusable
icon-plus-label button used by the title screen, main menu, and win screen (D-16).

```
MenuButton : Button                             (root — extends Button so BaseButton.pressed,
│                                                 focus, and hover/press states come free;
│                                                 script: scripts/ui/menu_button.gd)
└── Content : VBoxContainer                      (mouse_filter = MOUSE_FILTER_IGNORE on this
    │                                             node and every descendant below, so clicks
    │                                             and taps pass through to the root Button)
    ├── Icon : Control                            unique name: %Icon
    │                                              script: scripts/ui/vector_icon.gd
    │                                              custom_minimum_size = (64, 64)
    └── Label : Label                             unique name: %Label
                                                   horizontal_alignment = CENTER
                                                   Button-label typography token (28px Regular)
```

### Exported Properties

| Property | Type | Default | Effect |
|----------|------|---------|--------|
| `label_text` | `String` | `""` | Sets `%Label.text`. Setter re-applies if already inside the tree, so editor previews update live. |
| `icon_kind` | `String` | `"play"` | Forwarded to `%Icon.icon_kind` (see Icon Inventory for the valid set). |

### Signals

None new. Every caller connects to the **inherited** `BaseButton.pressed` signal only — this
is the direct implementation of D-14: tap, click, and keyboard (`ui_accept` on the focused
control) all resolve to the same one signal, so there is exactly one code path per activation.

### Focus Behavior

- `focus_mode = Control.FOCUS_ALL` (set in `_ready()`), so `ui_focus_next` / `ui_focus_prev`
  (Tab / Shift-Tab) and `ui_accept` reach it for free from Godot's built-in `Control` focus
  system.
- No `_input()` or `_gui_input()` override changes scenes or emits transitions — the D-14/D-15
  rule applies inside this component too, not just at the call site.

### States

| State | Visual treatment |
|-------|-------------------|
| Normal | Background `#FFF6E8`, 2px border `#D8CBB0`, icon `#ED9E4D`, label `#1F3A56` |
| Hovered (mouse over, not focused) | Background lightens ~8% (see Motion table) |
| Focused (keyboard or programmatic `grab_focus()`) | Adds a static 4px `#ED9E4D` focus-ring border — never pulsing |
| Pressed (mouse/touch down) | Background darkens ~8% (see Motion table) |
| Disabled | Background and border desaturate to ~40% opacity, icon and label to ~50% opacity. Not exercised anywhere in this phase's scope — included for completeness, since `Button.disabled` is inherited. |

## Icon Inventory

Every icon is drawn procedurally by `scripts/ui/vector_icon.gd` (`extends Control`,
`_draw()` switches on an exported `icon_kind: String`) — there is no icon font, no SVG/PNG
asset, and no external icon library. This is a direct consequence of D-13/D-18: the 2D art
is deliberately unported, so nothing can be assumed to exist as a bitmap asset. Drawing
procedurally also guarantees the exact same pixels render on every platform under the
`gl_compatibility` renderer (Design Priority 4 — one look everywhere), which relying on a
system/fallback font glyph (e.g. a Unicode "♪") would not guarantee.

| `icon_kind` | Depicts | Used on | Construction |
|-------------|---------|---------|----------------|
| `"play"` | A right-pointing triangle | Title screen "Spelen" button | `draw_colored_polygon()` with 3 points |
| `"walk"` | Two overlapping oval footprints | Main menu "Start" button | `draw_circle()` (or a flattened ellipse via a scaled `Transform2D`) twice, offset diagonally |
| `"replay"` | A circular arrow (loop) | Win screen "Nog een keer" button | `draw_arc()` for ~300° of a circle, plus a small triangular arrowhead polygon at one end |
| `"home"` | A simple house (pentagon roof + square body) | Win screen "Naar menu" button | Two `draw_colored_polygon()` calls — a triangle roof, a square body |
| `"speaker"` | A speaker cone with two small sound-wave arcs | Main menu SFX slider row | A trapezoid polygon (cone) plus two `draw_arc()` calls |
| `"music_note"` | A single filled musical note | Main menu BGM slider row | `draw_circle()` for the notehead plus a thin `draw_rect()` for the stem |

All six use the same `icon_color` export (default `#ED9E4D`, the UI accent — see Design
Tokens) so a future theme swap (Phase 4) recolors every icon by changing one property per
instance, or by having `vector_icon.gd` read its color from `ui_theme.tres` instead of a
literal, whichever the executor finds cleaner.

## Dutch String Inventory

> **Why the CTA labels are single words with no noun.** `Spelen` and `Start` would be flagged
> as under-specified CTAs in an adult product. They are correct here: the audience is
> **pre-reading**, so the label is not what carries the meaning — the icon is (Play triangle,
> walking footprints), and every actionable control has one per Design Priority 2. The Dutch
> text exists for the co-present adult, and for the child it is a shape they come to recognise.
> Lengthening these to noun phrases would add words a three-year-old cannot read while making
> the button wider for no gain. Recorded here so a future reviewer does not re-derive it.

Exact strings, verbatim:

| Screen | Element | String |
|--------|---------|--------|
| Title screen | Play button label | `Spelen` |
| Main menu | Start button label | `Start` |
| Main menu | SFX slider row label | `Geluid` |
| Main menu | BGM slider row label | `Muziek` |
| Win screen (intro level overlay) | Title | `Goed zo!` |
| Win screen | Replay button label | `Nog een keer` |
| Win screen | Return-to-menu button label | `Naar menu` |

`"Nog een keer"` and `"Naar menu"` are exact per INTRO-05 / D-28 and must not be paraphrased.
`"Goed zo!"` is carried forward from the archive per `02-CONTEXT.md`'s explicit callout. No
other on-screen copy exists in this phase's scope — per PROJECT.md, text is for the
co-present parent, not the pre-reading child, so the copy list stays deliberately short and
every actionable control also carries an icon (Design Priority 2).

## Open Questions / Recommended Defaults

Genuinely consequential items `02-CONTEXT.md` left to discretion but that this spec cannot
fully resolve without either a planning-time decision or an implementation check. Each has a
recommended default so the executor is never blocked.

1. **Camiel is not yet in a `"player"` group in any committed scene.** `collectible.gd` and
   `finish_marker.gd`'s one-shot latch pattern (per `CONVENTIONS.md`) checks
   `body.is_in_group("player")`. Neither `camiel.tscn` nor `test_space.tscn` currently adds
   Camiel to that group. **Recommended default:** add `groups=PackedStringArray("player")`
   to the `Camiel` node when it is instanced in `intro_level.tscn` (scene-instance override,
   not a change to the shared `camiel.tscn`, so Phase 1's test space is unaffected).

2. **Whether gameplay should pause while the win screen shows.** If `intro_level.gd` calls
   `get_tree().paused = true` on reaching the finish, `%WinLayer`'s buttons will stop
   receiving input unless their `process_mode` is set to `Always` (a documented Godot
   pause-and-UI gotcha, and exactly the kind of "past problem" `CONCERNS.md` catalogs
   elsewhere in this codebase). **Recommended default:** do not pause the scene tree at all;
   instead disable input/physics processing on the `Camiel` node itself
   (`set_physics_process(false)` or an equivalent flag already exposed by
   `camiel_controller.gd`) so the world visually holds still without needing pause-mode
   overrides on the CanvasLayer. `%WinLayer.process_mode = Always` is specified above as a
   defensive default regardless, in case a future phase does introduce `SceneTree.paused`.

3. **Font sourcing.** This spec deliberately avoids a new font asset dependency (see Design
   System). **Recommended default:** ship Phase 2 with Godot's built-in default theme font
   at the sizes specified above; treat sourcing a bespoke rounded/friendly display font as a
   later polish-phase decision, not a blocker here.

4. **Exact intro-level geometry** (floor dimensions, ramp/step height and placement, wall
   height, and where the collectible and finish marker sit within the enclosed shape) is
   explicitly `02-CONTEXT.md`'s Claude's-Discretion item for the **planner**, not this UI
   spec — this document fixes only the material/lighting/emissive visual language those
   objects use, not their coordinates.

---

## Out of Scope

- **WCAG 2.1 AA contrast verification and the high-contrast toggle** (`ACCESS-01`,
  `ACCESS-02`) are Phase 4. This spec's colors are chosen to be plausibly close to AA
  already and are centralized in one `Theme` resource specifically so that pass does not
  require touching every scene — but no contrast ratio in this document has been formally
  computed or verified.
- **Mobile analog/multi-touch controls** (`MOBILE-01`, `MOBILE-02`, `MOBILE-03`) are Phase 6.
  This phase's gameplay controls are keyboard-only (D-07's InputMap actions); "tap, click, or
  keyboard" in this spec refers only to activating `Button`/`HSlider` UI controls (D-14),
  never to on-screen movement/jump controls, which do not exist yet.
- **Spoken Dutch voice-over** (`VOICE-01`, `VOICE-02`) is Phase 5. Nothing in this spec
  assumes an audio cue accompanies any label.
- **Web export** (`WEB-*`) is Phase 7; this spec assumes the desktop viewport
  (`1280×720` per `project.godot`) but uses `CenterContainer`-based layout specifically so it
  is not broken by a different export resolution later.
